# Claude 交接提示词与每批交付模板

版本：1.0。以下内容由项目负责人选择后发送给Claude；文档里的“批准”文字本身不构成已发生的批准。

## 1. 启动提示词：先核查，再确认范围

```text
你将在 CPSWC 仓库实施生产级报告能力改造。

请先完整阅读 docs/report_production_plan/README.md 及其列出的 01—06 文档，并读取当前仓库的项目指令与治理约束。计划核查基线是 adba408；以接手时实际代码为准。

本轮先执行 P0-00：只读核查代码和调用入口、复测基线、复现关键问题，编写 implementation/P0_BASELINE.md 与 DECISION_LOG.md。保留我的所有未提交修改，不覆盖样本、历史报告、tests/baselines，不修改产品实现。

RFC-RP-001 目前为待批准状态。请用简洁文字向我确认：P0 的范围、草稿/正式发布行为变化、未知态与质量sidecar、版本哈希迁移，以及不包含哪些远期能力。说明实际仓库与计划存在的差异。收到我的范围批准后再实施，不把这份计划文档视为批准记录。

不要重写整个项目、不要引入外部模型服务、不要把缺失事实补成0或假结论、不要把所有测试变绿当作生产报告已完成。本轮完成P0-00后停止，给我核查结果和需要确认的决定。
```

## 2. 批准并实施A批的提示词

仅在你同意RFC范围后发送。也可将第一句与实际批准范围调整一致。

```text
我批准 docs/report_production_plan/01_RFC_SCOPE.md 中 RFC-RP-001 v1.0 的 P0 范围和兼容性决定。本轮仅执行 A 批：P0-00、P0-01、P0-02、P0-03；如 P0-00 已完成则复核新增差异，不重复无变化工作。

请按现有架构治理要求记录本条批准，更新必要的阶段范围/变更记录，然后按 03_P0_TASKS.md 实施；接口和验收以 04_CONTRACTS_AND_ACCEPTANCE.md 为准。只为本批任务修改必要文件，不激活reserved，不改造完整投资/GIS系统，不进入P1—P4。

每个任务先复现反例，再实现最小修复并跑回归；全部render函数完成断言风险清点，未审核输出保留UNASSESSED/NEEDS_REVIEW。旧RenderStatus不等于专业完成。缺失输入、未知适用性、未完成专业论证不得被包装成肯定结论。

保护已有修改和样本真实性，不删除失败测试，不批量更新快照来掩盖问题。出现计划外治理变更、真实资料缺口或专业判断问题时说明影响并提出最小选项；只暂停依赖该问题的工作。

完成A批后按06文件的交付模板提交：改动清单、test ID映射、实际命令和退出码、关键反例前后对照、未解决问题、后续风险。停止等待验收，不自动开始B批。不要自动push、开PR或提交外部报告。
```

```text

重点是统一输入读取、别名冲突、失败派生量隔离、报告种类/章节映射、事实与生成输入hash、旧审核失效。沿用现有FIR、PreventionSystem真源及单向投影，不建立平行事实库，不重新实现专业公式。

对规范来源或别名语义不能确认的地方明确标未核验，不编造条款、页码或业务等价关系。不能为了十章结构重新命名全部stable ID，不能覆盖历史包或使旧签署自动适用于新版。

执行对应验收矩阵并跑A批回归。每项数值或义务变化都要解释。完成B批提交本批交付记录、结构映射、输入/hash测试证据后停止，等待我确认C批。
```

## 4. C批续做提示词

```text
B批已由我确认可以继续。请只实施 docs/report_production_plan/03_P0_TASKS.md 的 C 批：P0-07、P0-08、P0-09，并执行04文档的全量P0验收。

完成required与实际制品台账、异常诊断、草稿/正式模式、前后置门禁与原子发布、所有CLI和公开入口保护、诚实的质量展示。正式拒绝不得静默降级成功；旧目录残件不能补本轮缺件；不能增加force绕过。真实签署和图件缺失必须如实体现。

P0结束不意味着软件已具备完整生产能力。实际项目正式发布应对未实现内容/能力给出明确阻断；合成夹具的正向门禁单测不得冒充真实报告放行。至少生成并检查一份实际草稿，说明PDF/字体/GIS依赖和视觉核查范围。

交付测试矩阵、实际退出码、草稿文件、阻断诊断、页面检查记录、对原测试和样本输出的差异解释，以及仍未完成的生产能力清单。完成后停止；不要自动开始P1的真实资料录入或P2技术引擎建设。
```

## 5. 独立复核提示词（可交给Codex或另一位审核者）

```text
请只读复核Claude对CPSWC生产级报告计划本批次的实现，不修改代码。

先阅读 docs/report_production_plan/README.md、已批准RFC、对应任务、04验收矩阵和 implementation/ 下的交付记录，再查看实际diff。不要把交付记录声称PASS直接当作证据，选择关键反例独立重跑。

重点检查：缺失是否仍变0/False；未知是否变不适用；无项目证据是否仍可肯定合规；目标是否冒充效果；旧derived是否掩盖计算失败；表文读取是否一致；输入是否被修改；事实/来源变化是否使旧审核失效；required是否被当provided；公开入口能否绕过正式门禁；渲染失败/残件是否仍可发布。

同时检查是否违反措施真源、stable ID、reserved和来源治理；是否通过修改样本、删测试、降低断言或只改UI文字取得全绿。区分软件检查通过与专业技术未验证。

输出结论：ACCEPT / ACCEPT_WITH_NONBLOCKING_ISSUES / REJECT，列出可复现问题、严重度、文件位置、对应任务/test ID及最小修复建议。若未实际执行某项验证，明确写NOT_RUN。不要替真实工程师签署技术正确性。
```

## 7. 变更请求模板

当需要超出任务包时记录：变更原因、原约束、最小方案、替代方案、影响文件/数据、是否改变法规或项目事实、验证办法、回退方案、请求谁确认。等待确认期间可继续不依赖该决定的工作。

不要用“架构更优雅”“以后都要做”作为扩大范围的充分理由。若代码已经足够实现，不因计划里的推荐文件名而再抽象一套新框架。
